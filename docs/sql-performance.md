# Query performance study

Sensorline's queries were written against a few thousand rows. This is what
happened when the `reading` table grew to a few million, how I profiled the slow
paths, and the fixes — measured, not guessed.

## Setup and honesty

- **Data:** synthetic, generated by `db/perf/seed.sql` — 40 devices, ~30 days of
  readings at 30s cadence, **3,457,740 rows (~1 GB with indexes)**. Not real
  device data. Rows are inserted in `sampled_at` order to model append-only
  ingestion (this matters for Case 1).
- **Engine:** PostgreSQL 16.15, running in the project's Docker Compose, on my
  local machine. Absolute milliseconds are hardware-specific; the point is the
  *shape* of the change (plan, buffers, ratio), which is portable.
- **Method:** `EXPLAIN (ANALYZE, BUFFERS)`, warm cache (each query run once to
  warm, then measured), so before/after are compared on equal footing.
- **Reproduce:** `bash db/perf/run.sh` (queries in `db/perf/queries.sql`, fixes
  in `db/perf/optimize.sql`).

The schema was already indexed sensibly (unique key on
`(device_id, metric, sampled_at)`, plus `(device_id, sampled_at DESC)` and
`(metric, sampled_at DESC)`). So these are not "forgot an index" fixes — they are
the access patterns those indexes don't serve, which is where scale actually
bites.

## Case 1 — Fleet-wide time-range aggregate → BRIN index

```sql
SELECT metric, count(*), avg(value)
FROM reading
WHERE sampled_at BETWEEN now() - interval '3 days' AND now() - interval '2 days'
GROUP BY metric;
```

**Before.** The filter is on `sampled_at` alone. Every existing btree index leads
with `device_id` or `metric`, so none can seek on time — the planner falls back
to a full scan:

```
Parallel Seq Scan on reading (actual time=230..268 rows=38400 loops=3)
  Rows Removed by Filter: 1114180
  Buffers: shared hit=16050 read=37146
Execution Time: 286.562 ms
```

3.45M rows scanned to return a 1-day slice.

**Diagnosis.** `reading` is append-only and physically ordered by `sampled_at`.
That physical correlation is exactly what a BRIN (Block Range Index) exploits: it
stores the min/max `sampled_at` per block-range and skips ranges outside the
filter, at a tiny fraction of a btree's size.

**Fix.**
```sql
CREATE INDEX reading_sampled_at_brin ON reading USING brin (sampled_at)
    WITH (pages_per_range = 32);
```

**After.**
```
Parallel Bitmap Heap Scan on reading (actual time=0.6..21 rows=38400 loops=3)
  -> Bitmap Index Scan on reading_sampled_at_brin (actual time=0.7 rows=18240)
  Buffers: shared hit=1840
Execution Time: 41.171 ms
```

| | Before | After |
|---|---|---|
| Execution | 286 ms | **41 ms** (~7x) |
| Buffers touched | 53,212 | 1,856 (~29x fewer) |
| Index size | — | **72 kB** (vs 293 MB for the `(device_id, metric, sampled_at)` btree) |

**Caveat, stated:** BRIN only helps because inserts are time-ordered. If rows
arrived badly out of order, the min/max per range would overlap and BRIN would
degrade toward a scan. For append-only telemetry that assumption holds.

## Case 2 — Latest reading per device → query rewrite (no new index)

Intent: the current value of every device/metric. Same data, three ways.

**2a, the naive version** — a correlated subquery:
```sql
SELECT r.device_id, r.metric, r.value, r.sampled_at
FROM reading r
WHERE r.sampled_at = (
    SELECT max(r2.sampled_at) FROM reading r2
    WHERE r2.device_id = r.device_id AND r2.metric = r.metric);
```
```
Seq Scan on reading r (actual time=137..48010 rows=43)
  SubPlan 2 -> Index Only Scan ... (loops=3457740)
  Buffers: shared hit=13846891
Execution Time: 48,053 ms
```
The subquery runs **once per row — 3.45M times**. 48 seconds.

**2b, `DISTINCT ON`** — correct and far simpler, but it sorts the whole table:
```sql
SELECT DISTINCT ON (device_id, metric) device_id, metric, value, sampled_at
FROM reading ORDER BY device_id, metric, sampled_at DESC;
```
```
Sort Method: external merge  Disk: 169200kB
Execution Time: 7,131 ms
```
7 seconds — better, but it still reads and sorts all 3.45M rows on disk.

**2c, the right fix** — there are only ~43 device/metric series. Seek the latest
of each with a `LATERAL` join over the existing `(device_id, sampled_at DESC)`
index instead of touching the fact table in bulk:
```sql
SELECT d.id AS device_id, lr.metric, lr.value, lr.sampled_at
FROM device d
CROSS JOIN LATERAL (
    SELECT metric, value, sampled_at FROM reading r
    WHERE r.device_id = d.id ORDER BY sampled_at DESC LIMIT 1) lr;
```
```
Nested Loop (actual time=0.03..0.32 rows=43)
  -> Seq Scan on device (rows=43)
  -> Limit -> Index Scan using reading_device_time_idx (loops=43)
  Buffers: shared hit=173
Execution Time: 0.397 ms
```

| | 2a correlated | 2b DISTINCT ON | 2c LATERAL |
|---|---|---|---|
| Execution | 48,053 ms | 7,131 ms | **0.397 ms** |
| Buffers | 13.8M | 53k + 169 MB temp | 173 |

**48 s → 0.4 ms**, no new index — just matching the query to the data's shape
(few series, one index seek each). This is the loose-index-scan / skip-scan idea
that Postgres doesn't do automatically.

**Caveat — the magnitude is cardinality-dependent, not row-dependent.** The 0.4 ms
comes from there being only ~43 series: 43 index seeks. The cost of this shape
scales with the *number of series*, not the number of rows — at 100k series it is
100k seeks and would land in the tens-of-ms to seconds range (still far below the
correlated subquery, but no longer 0.4 ms). The technique stays correct at any
cardinality; only the headline number depends on there being few series. For very
high series counts you would either batch the seeks or maintain a `latest_reading`
summary table updated on ingest, turning the read into a single indexed scan.

## Case 3 — Hourly dashboard rollup → materialized view

```sql
SELECT device_id, date_trunc('hour', sampled_at) AS hour, metric,
       avg(value), min(value), max(value), count(*)
FROM reading
WHERE sampled_at >= now() - interval '7 days'
GROUP BY device_id, hour, metric;
```

**Before.** Even with BRIN pruning the scan, every dashboard load re-aggregates
~800k rows:
```
HashAggregate (actual time=495..497 rows=6732)
  -> Bitmap Heap Scan on reading (rows=804140)
Execution Time: 527.220 ms
```

**Fix.** Precompute the rollup once and index it (`db/perf/optimize.sql`):
```sql
CREATE MATERIALIZED VIEW reading_hourly AS
SELECT device_id, date_trunc('hour', sampled_at) AS hour, metric,
       avg(value) AS avg_value, min(value) AS min_value,
       max(value) AS max_value, count(*) AS n
FROM reading GROUP BY device_id, date_trunc('hour', sampled_at), metric;
CREATE UNIQUE INDEX reading_hourly_key ON reading_hourly (device_id, metric, hour);
CREATE INDEX reading_hourly_hour_idx ON reading_hourly (hour DESC);
```
The rollup is **28,852 rows (4.7 MB)** — the whole month of history, small enough
to keep hot.

**After.**
```
Bitmap Heap Scan on reading_hourly (actual time=0.2..1.0 rows=6692)
  -> Bitmap Index Scan on reading_hourly_hour_idx
Execution Time: 1.345 ms
```

| | Before | After |
|---|---|---|
| Execution | 527 ms | **1.3 ms** (~390x) |

**Tradeoff, stated:** a materialized view is stale between refreshes. Refresh it
on a schedule; the unique index lets `REFRESH MATERIALIZED VIEW CONCURRENTLY
reading_hourly` rebuild it without blocking readers. Good for dashboards that
tolerate minute-scale lag, not for live alerting (which reads `reading`).

## Case 4 — The processor's own evaluation query → bounded rescan + partial index

Unlike Cases 1–3, this is the query the system actually runs. `processor/__main__.py`
(`readings_with_stats`) computes each reading's trailing-window mean/std and checks
whether it has an `evaluated` stage, per device/metric:

```sql
SELECT id, value, mean, std, evaluated FROM (
  SELECT r.id, r.value,
         AVG(r.value) OVER w AS mean,
         COALESCE(STDDEV_POP(r.value) OVER w, 0) AS std,
         EXISTS(SELECT 1 FROM reading_stage s
                WHERE s.reading_id = r.id AND s.stage = 'evaluated') AS evaluated
  FROM reading r
  WHERE r.device_id = $1 AND r.metric = $2
  WINDOW w AS (ORDER BY r.sampled_at ROWS BETWEEN 20 PRECEDING AND CURRENT ROW)
) t ORDER BY id;
```

Profiled on device 10 (86,401 readings, all but the most recent 100 already
evaluated — a running processor's steady state).

**Before.** It windows the device's *entire history* every cycle, then throws away
the already-evaluated rows in Python:

```
Sort (external merge Disk: 3640kB) rows=86401
  -> WindowAgg rows=86401
     -> Gather Merge -> Sort (external merge) -> Parallel Bitmap Heap Scan on reading
  Buffers: shared read=54995
Execution Time: 785.646 ms
```

786 ms to (re)evaluate 100 new readings, and it grows with history forever.

**Diagnosis.** A streaming processor only needs the *unevaluated tail* plus enough
preceding rows to fill the trailing window — never the whole history. The fix is a
code change, not just an index: have the processor pass a `since` bound (its
last-evaluated timestamp, or `now() - lookback`) and add a partial index for the
`evaluated` check.

**Fix.**
```sql
-- partial index (db/perf/optimize.sql)
CREATE INDEX reading_stage_evaluated_idx ON reading_stage (reading_id)
    WHERE stage = 'evaluated';

-- the query the processor should issue: bounded by a passed-in `since`
... WHERE r.device_id = $1 AND r.metric = $2 AND r.sampled_at >= $3 ...
```

**After** (`since` = latest reading − 60 min, covering the pending tail + window
context; 121 rows scanned):
```
WindowAgg rows=121
  -> Index Scan using reading_device_id_metric_sampled_at_key on reading (rows=121)
  SubPlan 1 -> Index Only Scan using reading_stage_evaluated_idx (loops=121)
Execution Time: 1.0 ms
```

| | Before | After |
|---|---|---|
| Execution | 786 ms | **1.0 ms** (~785x) |
| Rows scanned | 86,401 | 121 |
| Sorts | 2x external merge (disk) | in-memory |

**A real nuance worth stating:** the `since` bound must be a concrete value the
app passes, *not* an in-query `(SELECT max(sampled_at) …)` subquery. With the
subquery, the planner can't estimate the cutoff's selectivity, overestimates the
row count, and both triggers JIT (~20 ms of compilation for a 121-row query) and
falls back to a sequential scan of `reading_stage` for the `EXISTS`. Passing a
literal/parameter cutoff fixes the estimate, and the plan above (~1 ms) follows.

**Implemented.** `processor/__main__.py` now keeps a `processor_checkpoint`
(device, metric → newest evaluated `sampled_at`) and bounds each rescan to
`window_anchor()` — the row `spike_window` positions before the checkpoint, so the
first new reading still has a full trailing window. Verified on the live 3.45M-row
table: a bounded `evaluate()` on device 10 clears its 100-reading backlog in ~52 ms
(the query itself ~1 ms; the rest is writing genealogy rows) versus the 786 ms
full scan, and `test_incremental_evaluation_via_checkpoint` proves nothing is
missed or double-evaluated across cycles.

**Honest limit:** the checkpoint assumes in-order arrival. A cold start against a
large pre-existing backlog still does one unbounded pass (no checkpoint yet), and
readings back-dated *below* the checkpoint (e.g. a `--backfill` load) aren't picked
up until the checkpoint is reset. Both are acceptable for a continuously-running
processor; late/out-of-order data is a known-hard problem left as a documented
edge, not silently mishandled.

## Summary

| Case | Fix | Before | After |
|---|---|---|---|
| Fleet time-range aggregate | BRIN on `sampled_at` | 286 ms | 41 ms |
| Latest per device | LATERAL index-seek rewrite | 48,053 ms | 0.4 ms |
| Hourly dashboard rollup | Materialized view | 527 ms | 1.3 ms |
| Processor evaluation query (real hot path) | Bounded rescan + partial index | 786 ms | 1.0 ms |

The BRIN and the partial index graduate into `db/schema.sql` for production; the
rollup lives in `db/perf/optimize.sql` because it needs a refresh schedule. The
`LATERAL` rewrite and the bounded processor query are how those queries should be
written once the data got large — Case 4 additionally needs the processor to pass
a `since` checkpoint.
